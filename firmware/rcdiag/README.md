# rcdiag —— 遥控器按键诊断固件

**不是产品固件**，是查"按键脚是不是被硬拉死"的仪器。烧进遥控器的 C3 就能用。

它干两件事：

1. **全脚扫描**：对每个 GPIO 轮流开内部上拉、内部下拉各读一次
   | PU | PD | 判读 |
   |---|---|---|
   | 1 | 0 | 脚是自由的，上拉拉得动 = 正常 |
   | 0 | 0 | 45kΩ 上拉都拉不高 = 被低阻路径拉死在地 |
   | 1 | 1 | 拉死在 VDD |

2. **弱驱探测**：把按键脚设成输入+输出、驱动能力调最弱（约 5mA）、输出高，读回自己和另外两条
   - 自己读回 0 → 金属级死短（阻抗 < 约 100Ω）
   - 自己读回 1 → 之前的低电平是 kΩ 级弱拉（助焊剂/漏电），不是死短
   - 另外两条跟着变 1 → 三条网络彼此短在一起，而不是各自对地短

**为什么要有对照脚**：`GPIO5/6/7/10/20/21` 在遥控器 PCB 上什么都没接，它们必须读到 `PU=1 PD=0`。
只有对照脚是好的，那几条 `PINNED LOW` 的结论才立得住。**只量疑似有病的点、没有健康样本，就会被测量假象骗**
（2026-09-13 用万用表断电量通断连着测错两轮，就是栽在这上面）。

`GPIO2 / GPIO8 / GPIO9` 读到 `PINNED HIGH` 是正常的 —— 分别是 strapping 上拉、板载 LED、BOOT 上拉。

## 附带好处

**不深睡、不开射频**，所以串口一直在。正式固件在按键短路时会每 11.4 秒深睡唤醒一轮、
USB 整个掉线重枚举，`monitor` 根本挂不住。

## 用法

```powershell
robocopy "D:\玩具\01.道闸门\firmware" "D:\fw" /MIR /XD build .git
& "C:\Espressif\tools\Microsoft.v6.1.PowerShell_profile.ps1"
cd D:\fw\rcdiag
idf.py build
idf.py -p COM# flash
```

⚠ **打印一律用 ASCII**：中文经 USB-JTAG 读回来是 `??`，白白干扰判读。

⚠ **读日志要写成"反复重开端口累加"的循环**：芯片一复位，C3 的原生 USB 整个重新枚举，
之前打开的串口句柄当场作废。开一次读到底会读到 0 字节。

⚠ **别用 `DtrEnable=$false` + 脉冲 RTS 去复位 C3** —— 那组合在 USB-Serial-JTAG 上等于"按住 BOOT"，
每次都送进下载模式。最可靠的复位是**让用户拔插一次 USB**。
